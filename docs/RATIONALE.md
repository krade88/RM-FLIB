# Почему этот стек и именно такой порядок этапов

Этот документ объясняет два решения, зашитых в roadmap:

1. **почему выбран именно этот технологический стек;**
2. **почему этапы идут именно в таком порядке.**

Roadmap оптимизирован не под «изучить всё», а под конкретную цель: **с нуля дойти до работающей full-stack платформы уровня FogrestRead / FLIB** и получить портфолио, которое можно показать работодателю или использовать как основу продукта.

---

## 1. Целевой стек

Стек взят из реального FLIB, а не собран из популярных технологий:

- **Backend:** PHP 8.3, Laravel 13
- **Frontend:** Vue 3, Inertia 2, TypeScript, Vite, Tailwind CSS 4
- **Данные:** MySQL 8.4 в production, SQLite для локальной разработки и тестов
- **Кэш, сессии, очереди:** Redis
- **Real-time:** Laravel Reverb + Laravel Echo
- **Качество:** Pest, PHPStan/Larastan, Pint, ESLint, Prettier, Vitest, Playwright, GitHub Actions
- **Эксплуатация:** Docker, Docker Compose, nginx, PHP-FPM, Supervisord, Let's Encrypt
- **Наблюдаемость:** Sentry, Laravel Pulse, health checks, Web Vitals
- **Продуктовые технологии:** Tiptap, PWA/offline, полнотекстовый поиск, обработка изображений, Telegram WebApp

Это важно: roadmap не пытается покрыть «вообще весь full-stack». Он покрывает стек, который нужен для продукта, похожего на FLIB, и оставляет за скобками то, что не даёт пропорциональной пользы на этом пути.

## 2. Почему именно эти технологии

| Слой | Технологии | Почему они | Что не выбрано и почему |
|---|---|---|---|
| Инструменты | Терминал, Git, GitHub, VS Code, Markdown | Без них нельзя работать: версии, ветки, код-ревью, документация | Специализированные IDE и GUI-клиенты — вторичны |
| Веб-фундамент | HTTP, DNS, браузер, DevTools | Понимание того, где живёт код и почему запрос падает | Учить фреймворк до понимания HTTP — значит лечить симптомы |
| Разметка и стили | HTML, CSS, Tailwind | Семантика, доступность, адаптив; Tailwind используется в FLIB | Bootstrap/готовые темы скрывают основы; Tailwind без CSS — «классы без понимания» |
| Язык фронтенда | JavaScript, затем TypeScript | JS — язык браузера; TS добавляет безопасность | TS до JS — учить типы без понимания runtime; Dart/Elm — вне целевого стека |
| Фронтенд-фреймворк | Vue 3, Vue Router, Pinia, Vite | Ровно то, что используется в FLIB | React/Angular/Svelte — второй фреймворк не нужен; Nuxt — Inertia уже решает задачу |
| Backend | PHP 8.3, Laravel 13 | Целевой стек; Laravel даёт auth, ORM, очереди, валидацию, тесты | Node/Symfony — смена стека без причины; «голый PHP» — слишком много ручной работы |
| Данные | SQL, MySQL, SQLite | Домен реляционный: пользователи, новеллы, главы, комментарии, команды | MongoDB как основная БД — связи и целостность важнее гибкой схемы |
| Кэш и очереди | Redis | Кэш, сессии, очереди, счётчики, real-time | Memcached — уже; Redis как основная БД — нет, это не его роль |
| Связка | Inertia.js | SPA без ручного API; так устроен FLIB | Отдельный REST SPA — больше кода и дублирования; API всё равно изучается в Advanced |
| Качество | Pest, PHPStan, ESLint, Prettier, Vitest, Playwright, CI | Автоматическая проверка, а не «вроде работает» | Только ручное тестирование — не масштабируется |
| Контейнеры | Docker, Compose, nginx, PHP-FPM, Supervisord | Воспроизводимое окружение и production-паритет | Kubernetes/микросервисы — преждевременная сложность для монолита |
| Эксплуатация | VPS, HTTPS, CI/CD, staging, Sentry, Pulse, бэкапы | Проект должен работать и быть наблюдаемым после деплоя | «Задеплою вручную и посмотрю логи» — не production-подход |

## 3. Принципы порядка

### 3.1. От видимого к невидимому

Сначала HTML/CSS и JavaScript — можно быстро увидеть результат в браузере. Затем Vue, потом PHP, SQL, Laravel и инфраструктура. Это поддерживает мотивацию: ученик не полгода пишет только конфиги.

### 3.2. От языка к фреймворку

- JavaScript → TypeScript → Vue
- PHP → SQL → Laravel Core
- Laravel Core → Redis → Laravel Advanced
- SQL → Eloquent
- Vue → Inertia

Фреймворк изучается после языка, на котором он написан. Иначе Laravel и Eloquent выглядят «магией», а ошибки непонятно где искать.

### 3.3. От одного процесса к системе

Локальный код → база данных → кэш и очереди → контейнеры → деплой. Каждый следующий слой требует понимания предыдущего. Docker в начале пути — это слой сложности без контекста; Docker после приложения — инструмент упаковки.

### 3.4. Сначала построить, потом проверять, защищать и эксплуатировать

Порядок этапов качества:

1. **Тестирование и качество** — после того как есть что тестировать.
2. **Безопасность** — перед упаковкой и деплоем.
3. **Docker** — после того как приложение работает и проверено.
4. **Деплой и эксплуатация** — после контейнеризации.
5. **Продукт** — когда есть все инструменты.

Это не значит, что тесты и безопасность появляются только в конце: они вплетены в PHP, TypeScript, Laravel Core и Advanced. Отдельные этапы — это углубление и систематизация.

### 3.5. Спираль, а не водопад

Темы повторяются на новом уровне:

- тесты — в PHP/TS, затем отдельный этап;
- безопасность — в auth/валидации, затем отдельный этап;
- производительность — в SQL/Redis, затем в метриках и нагрузке;
- Docker — сначала как способ поднять MySQL/Redis, затем как production-упаковка.

### 3.6. Чистые группы

Группы этапов остаются читаемыми:

- **Фундамент:** 0–3
- **Фронтенд:** 4
- **Бэкенд:** 5–9
- **Связка:** 10
- **Качество и эксплуатация:** 11–14
- **Продукт:** 15–16

Это не только визуальная логика, но и зависимость: backend-этапы идут подряд, bridge-этап — после них, quality/ops — перед продуктом.

## 5. Ключевые переходы и компромиссы

### JavaScript → TypeScript

TypeScript изучается после JavaScript, потому что TS — надстройка над runtime-поведением JS. Если начать с типов, студент не понимает, что именно типизирует. JS даёт event loop, замыкания, DOM и асинхронность — без них TS превращается в «синтаксис ради синтаксиса».

### Vue → PHP

Фронтенд идёт раньше бэкенда по двум причинам:

1. Быстрый видимый результат поддерживает мотивацию.
2. Vue можно учить независимо, а Laravel требует PHP, SQL, окружения и понимания запроса.

Это не единственный возможный порядок. Для backend-first ученика PHP и SQL можно поставить раньше Vue, но тогда исчезает быстрый визуальный прогресс.

### PHP → SQL → Laravel Core

SQL стоит после PHP, потому что синтаксис и ООП дают язык для описания данных, но **до Laravel** — это обязательно. Eloquent без понимания SQL и связей превращается в набор магии. MySQL и SQLite выбраны потому, что FLIB использует MySQL в production и SQLite в тестах/локально; переход между ними — реальный навык.

### Laravel Core → Redis → Laravel Advanced

Redis перенесён после Core:

- в Core уже есть каталог, главы, авторизация и сессии, которые можно кэшировать;
- Redis изучается не в вакууме, а как инструмент Laravel-приложения;
- Advanced сразу использует Redis для cache, queues и broadcasting.

Если поставить Redis до Laravel, это будет абстрактный этап «команды redis-cli без приложения».

### Laravel Advanced → Inertia

Это осознанный компромисс. Логически Inertia можно поставить раньше Advanced, чтобы UI-интеграция появилась сразу после Core. Но тогда ломается чистая группировка «Бэкенд 5–9 → Связка 10». В текущем порядке backend-возможности изучаются до UI-слоя, а продукт затем связывает их через Inertia.

Если приоритет — «быстрее увидеть продукт в браузере», можно перенести Inertia перед Advanced. Тогда группы придётся перестроить, а прогресс сбросить.

### Тестирование после Inertia

Отдельный этап тестирования стоит после полного стека, потому что именно там появляются Laravel feature-тесты, Vue-компоненты, Inertia-страницы и E2E-сценарии. Но тесты не откладываются до этапа 11: в PHP и TypeScript уже есть темы PHPUnit/Pest и Vitest, а в Laravel Core/Advanced — feature-тесты.

### Безопасность перед Docker и деплоем

Безопасность — не «последний чеклист», а этап перед публикацией. Auth, policies и валидация появляются раньше, а здесь добавляются OWASP, CSP, rate limiting, секреты и бэкапы. Логика: не упаковывать и не деплоить приложение, пока не закрыты критичные риски.

### Docker после приложения

Docker — инструмент окружения, а не язык. Полный этап включает nginx, PHP-FPM, Supervisord, MySQL/Redis, production-конфиг. Это требует понимания Laravel, очередей, Redis и процессов. Раньше имеет смысл только **Docker Lite**: поднять MySQL/Redis в контейнерах и понять порты/volume. Полный Docker — после того как приложение работает и протестировано.

### Почему не React, Kubernetes, GraphQL и MongoDB

- **React/Angular/Svelte:** FLIB использует Vue; второй фреймворк на этом пути — трата времени.
- **Kubernetes/микросервисы:** для монолита на VPS достаточно Docker Compose; K8s добавляет сложность без продукта.
- **GraphQL:** Inertia и REST закрывают потребности; GraphQL не в стеке FLIB.
- **MongoDB как основная БД:** домен реляционный; связи, целостность и транзакции важнее гибкой схемы.
- **NoSQL/очереди без SQL:** Redis — дополнение, а не замена реляционной БД.

## 6. Что изменилось бы при другой цели

| Цель | Что поменять |
|---|---|
| DevOps/SRE | Docker и эксплуатацию раньше; больше Linux, сетей, CI/CD, IaC |
| Frontend | Больше Vue, дизайна, accessibility, производительности; PHP/Laravel — минимально |
| Backend | PHP, SQL, Redis и Laravel раньше; фронтенд — до уровня интеграции |
| Быстрый MVP | Laravel + Inertia + SQLite; Redis, Docker, real-time и PWA отложить |
| Трудоустройство | Добавить CS-базу, soft skills, mock-интервью и open source параллельно |

## 7. Вывод

Порядок не является единственно правильным. Он оптимизирован под конкретный сценарий:

- один человек учится с нуля;
- цель — full-stack продукт, похожий на FLIB;
- нужен баланс между пониманием основ и скоростью выхода к работающему приложению;
- каждая группа этапов заканчивается практикой и артефактом;
- тесты, безопасность и производительность сначала появляются как темы, затем — как отдельные этапы.

Главная идея: **сначала язык и данные, потом фреймворк, потом кэш и real-time, потом качество/безопасность, потом контейнеры и эксплуатация, и только затем — продукт.** Это минимизирует «магию», сохраняет мотивацию и приводит к результату, который можно задеплоить и показать.
